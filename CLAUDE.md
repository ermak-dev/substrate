# Substrate for Brood

Форк Agent Substrate для Brood. Добавляем экспериментальный класс `lxc`
для доверенных долгоживущих нагрузок. Полная VM (`fullvm`) не входит в план.
План и интеграция: `https://git.ermak.dev/ermak/brood/-/blob/main/docs/LXC.md`.
Пока документ не опубликован, рабочая копия лежит в `../brood/docs/LXC.md`.

## Правила

- Прочитать `AGENTS.md`, `COLLABORATING.md` и `CONTRIBUTING.md`. Правила
  upstream применяются, кроме явно перечисленных отличий форка ниже.
- Код Substrate остаётся на Go. Python-only правило brood сюда не переносится.
  Соблюдать раскладку пакетов upstream и `docs/code-style-guide.md`.
- `origin` указывает на `git.ermak.dev/ermak/substrate`, `upstream` на
  `github.com/agent-substrate/substrate`. Module path сохраняется.
- Секреты не попадают в git, комментарии, вывод или настройки нод.
  Общий токен оператора не передаётся актору или воркеру.
- Не менять хостовые настройки, firewall, CNI или PVE без отдельного
  согласования. Спайки запускаются на выделенном стенде.
- Не добавлять hostPath, privileged, capabilities или unconfined-профили
  штатным классам ради `lxc`. Новые права ограничивать своим классом.
- Atelet и worker не зависят от устройства друг друга. Контракт остаётся в
  `internal/proto/ateworkerpb` и `internal/nodepath`.
- Не изображать disk backup как checkpoint памяти. Неподдерживаемая операция
  должна отказать до изменения живого актора, его назначения и томов.

## Отличия форка от upstream

- Только `lxc` допускает обычную Linux container isolation. Она слабее
  gVisor и microVM и не подходит для враждебной мультиарендности.
- Изменение только `lxc` не требует новой реализации на других рантаймах.
  Изменения общих путей проверяются на штатных классах.
- Issues и merge requests живут в GitLab этого репозитория. Изменения brood
  получают отдельные задачи и MR в brood. GitHub PR не открываем автоматически.
- Правило upstream про отсутствие ссылок на issues в сообщениях коммитов
  сохраняется. Ссылки и AI disclosure указываются в описании MR.

## Процесс

- Одна задача = один issue до кода. Перед созданием искать дубли среди
  открытых и закрытых issues и открытых MR.
- Трекер по-русски, ветки и коммиты по-английски. Названия и тела задач
  короткие: факт, доказательство, что изменить, критерий готовности.
- Метки по словарю brood: `type::feature`, `type::bug`, `type::docs`,
  `type::ci`, `type::epic`; статусы `status::live`, `status::wip`,
  `status::parked`, `status::fixed`, `status::noise`, `status::dup`.
  Отложенные задачи остаются открытыми. Не добавлять случайные метки.
- Ветка задачи: `[type]/[iid]-[slug]`, от свежей main. Один MR = одно изменение.
  Рефакторы и интеграцию brood отправлять отдельно.
- Сначала падающий тест нового поведения, затем минимальная реализация.
  Предпочитать строки существующей таблицы. Не использовать fixed sleeps.
- Перед ревью: проверить свой diff, выполнить `go test -race ./...` и
  `hack/verify-all.sh`. Новые тесты также прогнать с `-count=3 -shuffle=on`.
  Невыполненные проверки и причины явно назвать в MR.
- Для существенных изменений нужен свежий adversarial review агентом.
  Каждую находку проверить перед исправлением.
- MR начинает с причины или ссылки на issue, сообщает об использовании AI
  и не содержит co-author/assisted-by trailers. Коммит проверяет человек.
- Перед MR rebase на свежую upstream main. Исправления ревью и rebase
  отправлять отдельными push. Main интегрируется squash-merge.

## Работа с трекером

Можно использовать CLI brood с явным проектом, без копирования токена:

```
GITLAB_PROJECT=ermak/substrate ../brood/bin/brood dev bug list
GITLAB_PROJECT=ermak/substrate ../brood/bin/brood dev bug show <iid>
```

Brood определяет origin своей рабочей копии, а не текущего каталога.
Без `GITLAB_PROJECT` эти команды обратятся к задачам brood.
